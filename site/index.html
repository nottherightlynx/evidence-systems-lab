DBT + SQL · CRM migration PROJECT 01

Preserving identity and financial meaning across systems

Reconcile constituents, engagement and contributions while retaining source keys and unmatched events.

What is lost when a CRM migration treats source IDs and financial stages as interchangeable?

Technical flow

Legacy/new CRM and event/donation seeds → staging → reviewed identity crosswalk → event and contribution facts → dbt tests → lifecycle mart.

Engineering decisions

  • Keep original source IDs while relating verified identities through a bridge.
  • LEFT JOIN source events to the crosswalk for reconciliation, preserving unmatched interactions.
  • Keep received cash, pledges and refunds as different observed financial facts.
Open observed evidence and limitations

Evidence

  • Four fictional interactions, three matched events and one unresolved identity.
  • A duplicate event ID produced a dbt uniqueness-test failure; restoring the clean seed allowed the build to pass.
  • Two verified engaged people, one unresolved engagement, one $25 received payment, a $100 pledge and a $25 refund are present in the synthetic baseline.

What is not claimed

Prototype uses fixed fictional identities, not inferred matches or real CRM constituent data.

Experience it connects to

CFLeads Salesforce investment/renewal logic, TLC donor reconciliation, NAACP LDF CRM integrations.

PYTHON + DAGSTER · Public-source reliability PROJECT 02

Distinguishing missing data from missing events

Normalize inconsistent state-style feeds and expose freshness, schema changes and retrieval history.

If a jurisdiction returns no records, is the finding truly empty—or did ingestion fail?

Technical flow

Simulated State A/B feeds (+ optional official Federal Register metadata) → Python normalization → validation → source-status report → analyst review.

Engineering decisions

  • Keep source publication time distinct from retrieval time.
  • Reject unexpected source-schema changes rather than silently discarding a jurisdiction.
  • Label simulated sources as simulated and an unfetched official source as NOT_FETCHED_OFFLINE.
Open observed evidence and limitations

Evidence

  • An intentional State B field rename caused the normalizer to raise a ValueError.
  • After fixture restoration: three normalized simulated records; State A=2 and State B=1.
  • The official Federal Register was NOT_FETCHED_OFFLINE in the recorded offline run; a separate successful Dagster five-asset run was documented.

What is not claimed

Demonstrates source-quality handling, not comprehensive monitoring of real state legislation; the schema-failure example ran in the Python pipeline.

Experience it connects to

NCTE cross-state legislative monitoring and CFLeads geographic engagement reporting.

GOVERNED QUERIES · Evidence boundary PROJECT 03

Answers that preserve approved definitions

A deterministic question interface routes to allowlisted metrics, reports rule versions, and refuses unsupported requests.

Can natural-language-like queries access useful analytical results without changing the rules behind them?

Technical flow

Question → alias-based metric selection → simulated rule filtering → approved DuckDB/CSV calculation → traceable result or refusal.

Engineering decisions

  • The interface does not invent its own financial definitions.
  • Refuse unsupported causal, restricted, raw-SQL and date-filter requests.
  • Distinguish synthetic rule references from verified public source citations.
Open observed evidence and limitations

Evidence

  • Recorded results: two engaged people plus one unresolved event, and a $25 receipt with a separate refund.
  • The source-status answer reports zero stale feeds and one official feed not fetched.
  • The deterministic suite recorded 20/20 checks passing, covering supported metrics and explicit refusals.

What is not claimed

Deterministic phrase router; no LLM, general RAG, true authentication, or production authorization implemented.

Experience it connects to

CFLeads Data Wiki, investor and program metric governance, responsible AI pilot design.

METHOD AND LIMITATIONS

What the experiments do—and don't—prove.

Engineering approach

Preserve source identifiers and unmatched records; declare event grain; distinguish financial statuses; monitor geographic data-source health; keep queries within documented metric definitions.

Limits disclosed

No employer data, real voter information, complete source coverage, causal attribution, production authorization or deployed LLM is represented. A local language model does not independently establish privacy compliance.

Professional throughline

CRM investment and program data at CFLeads, data systems at TLC and NAACP LDF, legislative and voter analytics at NCTE, and SQL/data modeling experience at Quicken/Rocket Mortgage.
